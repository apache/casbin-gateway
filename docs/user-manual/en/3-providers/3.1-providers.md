# 3.1 Providers

A provider is one model endpoint Gateway can send an agent's requests to: a vendor, a reseller, or something running on this machine. **Providers** is the list of them.

[![New provider](https://cdn.casbin.org/img/casbin-gateway-new-provider.png)](https://cdn.casbin.org/img/casbin-gateway-new-provider.png)

## Adding one

**Providers** → **Add**:

| Field | What goes in it |
| --- | --- |
| **Type** | The API the endpoint speaks: OpenAI-compatible or Anthropic-compatible |
| **Base URL** | The vendor's endpoint, as its own documentation gives it |
| **API key** | The key Gateway will authenticate with — see [3.3](3.3-caller-login.md) for the case where there is none |
| **Models** | The models it serves. Leave it empty and any model name is accepted |
| **Authentication** | The key above, or **the caller's own login** ([3.3](3.3-caller-login.md)) |
| **Upstream API** | Which endpoint Gateway calls on it. Leave it on **From the type** unless the vendor says otherwise |

Gateway tests the endpoint before storing it, and from then on [Authenticity](3.4-authenticity.md) grades it on its own.

Vendors with an "add this provider" button on their own page can skip the form — see [3.5 Import settings and links](3.5-import.md).

## The type is not a restriction

The type says what the **provider** speaks, not what your agents must speak. Gateway translates between the four APIs in both directions, so an OpenAI-compatible provider serves an Anthropic client perfectly well ([3.2](3.2-routing.md)).

Which means the practical answer for most resellers is: whichever of the two their documentation describes.

## When the vendor serves the Responses API too

**Upstream API** is under **Advanced** on the add form, and on the provider's own page. It decides which path Gateway appends to the base URL: `/chat/completions`, `/responses`, or `/v1/messages`. **From the type** picks the first for an OpenAI-compatible provider and the last for an Anthropic one, which is right for nearly every vendor.

Set it to **Responses** when the endpoint serves that API as well. Two reasons to:

- A Codex client already speaks it. With Responses on both sides the request is relayed byte for byte instead of being translated twice, so nothing the canonical form does not model is lost.
- Some resellers report cached input more accurately on `/responses` than on `/chat/completions`. The cached count then reaches [LLM records](../4-governance/4.2-llm-records.md) as the upstream meant it, and is priced at the cache rate rather than at the full input rate.

The setting only changes the request Gateway sends upstream. Agents keep calling whichever API they speak.

## Anything with an endpoint

Roughly forty vendors and gateways are recognised by name, and anything else that speaks either API works the same way:

- **Vendors** — OpenAI, Anthropic, Google Gemini, xAI, Mistral, Cohere, DeepSeek, Moonshot, Zhipu GLM, MiniMax, StepFun, Baichuan and more.
- **Aggregators** — OpenRouter, SiliconFlow, Together, Groq, Fireworks, Novita, PPIO, AiHubMix, 302.AI, Vercel AI Gateway.
- **Clouds** — Bedrock-style endpoints, Aliyun DashScope, Volcengine, Tencent Cloud, Baidu, ModelScope, NVIDIA NIM.
- **Local** — Ollama, LM Studio, vLLM, llama.cpp, LiteLLM.

## Where the keys are kept

In Gateway's own database, on this machine. Two things are worth setting:

- `apiKeyEncryptionKey` encrypts provider API keys at rest with AES-256-GCM ([5.1](../5-operations/5.1-settings.md)).
- The keys never reach a record: request headers are not stored, and bodies are sanitized before they are ([4.2](../4-governance/4.2-llm-records.md)).

An agent routed through Gateway never receives the key at all — it gets Gateway's own relay token instead ([3.2](3.2-routing.md)).

## Which agents may use which provider

Per agent, on the **Permissions** page: any provider, or only the ones you pick ([4.1](../4-governance/4.1-permissions.md)).
