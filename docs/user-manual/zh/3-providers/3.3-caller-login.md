# 3.3 没有API Key：沿用调用方自己的登录

用ChatGPT或Claude订阅登录的Agent，手里根本没有API Key可粘。它也不需要。

把供应商的**认证方式**设成**调用方自己的登录**：

- 基础URL指向厂商。
- 每个请求都带着**Agent自己发来的凭据**转发出去，所以它保住了自己的登录态。
- **模型**留空，这个供应商就接受任意模型名。

Gateway记录和路由这类流量的方式，和有Key的供应商完全一样。它只是从头到尾没见过Key。

## 环境变量片段更短

这类供应商的片段只设基础URL，别的都不设：

```bash
export ANTHROPIC_BASE_URL="http://localhost:17000/v1/agents/claude-code"
```

在这里再放一个token，会**顶掉**Agent已有的登录——而保住那个登录正是这种模式存在的理由。

## 你仍然拿得到什么

除了"替它保管Key"以外的全部：

- 完整的LLM记录（[4.2](../4-governance/4.2-llm-records.md)）。
- 对工具、模型、供应商的权限控制（[4.1](../4-governance/4.1-permissions.md)）。
- 在会话记录已有数据之上，再加一份来自转发流量的用量（[4.3](../4-governance/4.3-usage-and-pricing.md)）。

## Codex

Codex的ChatGPT登录对接的不是OpenAI的API，而是Codex后端，所以它的供应商也指向那里：新建时选**ChatGPT订阅**这个来源，或者自己把基础URL填成`https://chatgpt.com/backend-api/codex`、上游API选Responses。

这时**写入配置**往`~/.codex/config.toml`里写的不是Key，而是`requires_openai_auth = true`——Codex由此把自己已有的ChatGPT登录发过来，Gateway原样转发上游，一个字都不留。

不管怎样，Codex的花费都会出现在[用量](../4-governance/4.3-usage-and-pricing.md)页上，因为那一页读的是Agent自己的会话记录，而不是转发记录。
